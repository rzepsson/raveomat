# Account Settings Dashboard — Implementation Plan

## Overview
Transform the read-only `TabSettings.svelte` into a fully interactive account settings page with:
1. Inline-editable profile fields (full name, phone, city)
2. Inline password change form (with OAuth provider detection)
3. Password reset email action

## Architecture

### Backend — New Astro Server Actions (`src/actions/settings.ts`)

Three new actions, all registered in `src/actions/index.ts`:

| Action | Input | Rate Limit | Logic |
|--------|-------|------------|-------|
| `updateProfile` | `{ fullName, phone, city }` | 10 req/15min per user | `supabase.from("profiles").update(...)` where `id = user.id` |
| `changePassword` | `{ currentPassword, newPassword }` | 5 req/15min per user | Verify current password via `signInWithPassword`, then `updateUser({ password })` |
| `sendPasswordReset` | `{}` | 3 req/60min per user | `supabase.auth.resetPasswordForEmail(email)` |

All actions use `context.locals.supabase` (server-side client with auth cookies) and require an authenticated user (throw `UNAUTHORIZED` if `context.locals.user` is null). Rate limiting uses the user's UUID as identity (hashed).

The `changePassword` action first re-authenticates by calling `signInWithPassword` with the current password to verify the user knows it, then calls `updateUser({ password: newPassword })`. This is necessary because Supabase's `updateUser` for password change works best when the session is fresh.

#### Identity Card (editable)
- **Edit toggle**: "EDYTUJ" button in the card header switches between read-only and edit mode
- In edit mode: fields become `<input>` elements with the same styling as `RegisterForm.svelte`
- Full Name: text input, min 2 / max 120 chars
- Phone: tel input, optional
- City: text input, optional
- Email: always read-only (shown as static text with a note that email change requires contacting support)
- Save/Cancel buttons appear in edit mode
- On save → calls `actions.updateProfile()`, then `loadUserProfile(userId)` to refresh the store
- Success/error feedback via `pushNotification()`

#### Security Card (password)
- Detects if user signed up via OAuth (check `user.app_metadata.provider`)
- **For email/password users**:
  - Collapsible/expanding form: click "Zmień hasło" to reveal the form inline
  - Fields: Current password, New password (min 8 chars), Confirm new password
  - Client-side validation: new password match, min length
  - On submit → `actions.changePassword()`
  - After success, collapse the form and show success notification
- **For OAuth users**:
  - Show info message: "Twoje konto jest zarządzane przez [Google/Apple]. Hasło jest obsługiwane przez dostawcę."
  - No password form
- **Password reset link**: "Wyślij link do resetowania hasła" button
  - Calls `actions.sendPasswordReset()`
  - Shows success notification: "Link do resetowania hasła został wysłany na Twój adres email."
  - Rate-limited to prevent abuse

#### Account Info Card (read-only)
- UUID
- Account creation date
- Auth provider (email, google, apple)
- Email verification status (badge: "Zweryfikowany" green / "Niezweryfikowany" yellow)

#### New Icons Needed
Add to `Icon.svelte`:

- `"eye"` / `"eye-off"` — for password visibility toggle

### No Database Changes
The `profiles` table already has `full_name`, `phone`, `city` columns with an RLS policy allowing users to update their own row (`auth.uid() = id`). No migration needed.

### Security Considerations
- All actions are server-side (Astro server actions) — no sensitive logic on the client
- Rate limiting on all actions using the existing `enforceRateLimit` infrastructure
- Password change requires re-authentication (verify current password before changing)
- Honeypot field not needed for settings (user is already authenticated, route is protected)
- Input validation via zod schemas on all actions
- No secrets or tokens exposed to the client
